#### 基本データ・イベントフロー（提案）

```text
ユーザー操作
    ↓
画面Component
    ↓
FormGroup / DTO
    ↓
Application
    ↓
Domain
    ↓
Repository Interface
    ↓
Infrastructure
```

取得結果は逆方向に戻し、最終的な表示判断を画面Componentが行う。

共通Componentはこの縦方向の業務フローには入らず、画面ComponentとFormControlの間にある再利用可能なUI部品として扱う。

```text
画面Component
    ├─ FormControl ── 共通入力Component
    └─ イベント  ←── 共通Component
```

## 2026-10-20 承認：フレームワークとアプリ固有設計の分離

- **承認済み**：BruceフレームワークはUI・Application・Domainの汎用的な責務境界のみ規定する。サーブ順・リターン側・テニスの業務規則、個別Domain API／戻り値の設計はテニスアプリ固有の別相談で扱い、フレームワークの必須設計対象にしない。
- 旧2.7.1／2.7.2のテニス固有項目は、汎用責務境界の確認に読み替える。既存の旧議事録は経緯として保持し、最新の承認を優先する。
- 汎用原則：UIは入力・表示・操作受付、Applicationはユースケース調整、Domainは業務規則と整合性保証。具体的な業務規則とAPIは各アプリが設計する。
- 個別のテニス業務ロジックを理由にBruceフレームワークの質問・実装を増やさない。
