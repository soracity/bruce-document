#### 承認済みIssue：レスポンシブ・折り返し

> 状態：**設計承認済み**  
> 承認日：2026-10-16

##### 基本原則

> **画面ComponentはレスポンシブCSSを直接記述せず、LayoutManagerが画面幅に応じた配置変更を担当する。**

画面Componentは何をどの順番で配置するかという構造だけを記述し、ブレークポイント・折り返し・row/column切替等のCSS実装を直接持たない。

##### 画面側でブレークポイントを直接指定しない

次のような画面実装は行わない。

```html
<div class="flex flex-col md:flex-row">
  ...
</div>
```

```html
<app-textbox class="w-full md:w-1/2" ... />
```

`sm:`、`md:`、`lg:`等のレスポンシブUtilityを画面HTMLに直接記述して配置を調整しない。

画面側は次のようにLayoutManagerを使用して構造を記述する。

```html
<app-layout-item>
  <app-textbox ... />
  <app-date ... />
</app-layout-item>
```

##### LayoutItemが折り返しを担当する

同一`LayoutItem`内のComponentを横並びで表示できる十分な横幅がある場合は横並びとする。

横幅が不足し、各Componentの操作性・視認性を維持できない場合は、`LayoutItem`が折り返して縦方向へ配置する。

```text
十分な幅：
Textbox | Date

幅不足：
Textbox
Date
```

画面Component自身は`flex-wrap`等を直接指定しない。

##### LayoutSpanと折り返し

`appLayoutSpan`で指定した比率は、**横並びで表示できる場合の配置比率**として扱う。

```html
<app-layout-item>
  <app-textbox [appLayoutSpan]="70" ... />
  <app-date [appLayoutSpan]="30" ... />
</app-layout-item>
```

十分な横幅がある場合は70:30で配置する。

横幅不足時には70:30を無理に維持せず、折り返した各Componentが利用可能な横幅を使用する。

##### Component単位のレスポンシブInputは現段階で追加しない

現段階では次のようなInputを追加しない。

- `minWidth`
- `responsiveBreakpoint`
- `wrapBreakpoint`

まずはLayoutManager側の共通ルールで対応する。実際の画面要件として一般ルールでは対応できないケースが複数発生した場合のみ、意味のある限定的API追加を検討する。

不要な抽象化や設定項目を初期段階から増やさない。

##### ItemStackLayoutの扱い

`ItemStackLayout`は行を縦方向に積み重ねる責務を持つため、通常はレスポンシブによる大きな方向変更を必要としない。

主なレスポンシブ・折り返し責務は`LayoutItem`が担う。

##### AI実装ルール

AIが画面を実装する場合も次を遵守する。

- 画面HTMLに`sm:`、`md:`、`lg:`等のレスポンシブUtilityを直接追加しない。
- 画面側に`flex-wrap`や独自メディアクエリを追加しない。
- 横並び・折り返しは`LayoutItem`の責務として実装する。
- `appLayoutSpan`は横並び時の比率として扱い、狭い画面で比率維持を強制しない。
- 既存LayoutManagerで対応できないレスポンシブ要件が出た場合、画面固有CSSで回避せず設計確認を行う。

### 2026-10-19：幅不足時はLayoutItemが自動折り返し（方式A・承認済み）

- **承認根拠**：本会話の選択肢「1. A：自動で折り返す（推奨）」にユーザーが「1」と回答。
- **基本動作の承認**：横並びの表示項目について利用可能幅が不足した場合、LayoutItemが自動で折り返し、項目が極端に狭くならないようにする。画面ごとの任意ブレークポイント直書きは避ける。
- **未決事項**：幅不足の具体的な判定基準（必要幅・閾値）、折り返し先の項目単位と行内LayoutSpan比率の扱い、全幅へ縦積みするか複数行へ折り返すか、入れ子・端末幅の例外は未承認。今回の「1」はこれらの詳細まで承認したものではない。
- **状態**：工程2.4.2は進行中／基本方針承認済／実装未着手／検証未実施。
- **次の議題**：幅不足時の折り返し形態（複数行配置か全項目縦積みか）。

### 2026-10-19：幅不足時は必要な項目だけ次行へ折り返す（方式A・承認済み）

- **承認根拠**：本会話の「1. A：必要な項目だけ折り返す（推奨）」にユーザーが「1」と回答。
- **承認仕様**：LayoutItemで横方向の必要幅が不足した際、全項目を一律に縦積みにするのではなく、収まらない項目を次の行へ順次折り返し、可能な項目は同じ行に残す。元の表示順序は保持する。
- **既承認との関係**：LayoutItemの自動折り返し方針を具体化する決定であり、画面ごとのブレークポイント直書きを求めない。
- **未決事項**：各項目の必要幅・判定閾値、折り返し後の行内LayoutSpan比率・合計100規則との整合、実装方式、テスト条件。
- **状態**：2.4.2進行中、設計一部承認、実装未着手、検証未実施。
- **次の議題**：折り返し後の各行でLayoutSpanの比率をどう扱うか。

### 2026-10-19：折り返し後は各行でLayoutSpanを再配分（方式A・承認済み）

- **承認根拠**：本会話の「1. A：行ごとに比率を再計算（推奨）」にユーザーが「1」と回答。
- **決定**：折り返しにより複数行となったとき、各行の表示項目だけを対象に元のLayoutSpanの**相対比率**を維持し、その行の利用可能幅を100%として再配分する。元のSpan値そのものは変更しない。
- **例**：Span 50・30・20の3項目が先頭2項目と最後1項目に折り返された場合、1行目は50:30（62.5%:37.5%）、2行目は20のみ（100%）。gapを除いた行ごとの幅を配分する。
- **既承認事項との整合**：テンプレートの元の兄弟Span値は合計100・全兄弟明示という静的検査規則を維持する。**折り返し後の行ごとにSpan合計100を別途要求しない**。
- **未決事項**：幅不足判定基準、項目の必要最小幅、行分割アルゴリズムや計算方法の詳細、実装・動作検証。
- **状態**：2.4.2設計一部承認・進行中。実装未着手、検証未実施。
- **次の議題**：各項目の必要幅を基準とするか、固定の画面幅閾値を基準とするかを決定する。

### 2026-10-19：項目ごとの必要幅で折り返し判定（方式A・承認済み）

- **承認根拠**：本会話の「1. A：各項目の必要幅で判定（推奨）」にユーザーが「1」と回答。
- **承認内容**：LayoutItemは画面幅の固定閾値ではなく、表示中の各項目に必要な最小幅とgap、およびLayoutItemの実際の利用可能幅を基準に、項目を次行に折り返すか判定する。画面別の一律ブレークポイント直書きは採用しない。
- **既承認との整合**：必要な項目だけを表示順に次行へ折り返し、各行の幅は行内のLayoutSpan相対比率で再配分する。元のテンプレート上の合計100規則は維持。
- **未決事項**：Component別の具体的な最小幅、その定義・取得・変更の仕組み、極端に狭い幅や長文の扱い、行分割アルゴリズム。例示した150px・140px・100pxは承認値ではない。
- **状態**：2.4.2は進行中・設計一部承認、実装未着手・検証未実施。
- **次の議題**：必要幅をComponent側の標準値として持つか、LayoutItem側の一律値で扱うか。

### 2026-10-19：必要最小幅の管理責務は各共通Component（方式A・承認済み）

- **承認根拠**：本会話の選択肢「1. A：各Componentが管理（推奨）」にユーザーが「1」と回答。
- **承認内容**：Textbox・Date・Buttonなど各共通Componentが、自身の表示に必要な最小幅の定義責務を持つ。LayoutItemは各項目の必要幅とgap・利用可能幅を考慮して折り返しを判定する。LayoutItemが全種類に一律の固定最小幅を押し付ける方式Bは採用しない。
- **未決事項**：各Componentの具体的な最小幅の数値、標準HTML要素・その他の子要素の必要幅の扱い、値の取得・通知方法、文字拡大時や極端に狭い画面への対応。

### 2026-10-19：表示内容に応じて必要最小幅を変化させる（方式B・承認済み）

- **承認根拠**：本会話の「1. B：内容に応じて変化させる（推奨）」にユーザーが「1」と回答。
- **承認内容**：共通Componentは自身の必要最小幅を管理し、標準的な幅を基準としつつ、ラベル・表示内容・文字サイズ・言語差異などによって必要幅を変化させる。Component種別ごとの完全固定値だけで判定する方式Aは採用しない。
- **既承認方針との整合**：LayoutItemは各Componentの必要幅とgap・利用可能幅を基準に必要な項目だけ折り返し、折り返した行ではLayoutSpanの相対比率を再配分する。
- **未決事項**：内容から必要幅を測る具体的方法、上限・下限や長文省略との関係、標準HTML要素の扱い、極端に狭い表示領域の挙動。具体的な幅・計算APIは未承認。
- **状態**：2.4.2進行中、設計一部承認、実装未着手・検証未実施。
- **次の議題**：長文などで必要幅が画面幅を超えた場合の基本動作を決める。

### 2026-10-19：必要幅が画面幅を超えるとき利用可能幅まで縮小（方式A・承認済み）

- **承認根拠**：本会話の選択肢「1. A：画面幅まで縮小する（推奨）」にユーザーが「1」と回答。
- **基本動作**：ある共通Componentの必要幅がLayoutItemの利用可能幅を超える場合、当該Componentを利用可能幅まで縮小する。必要幅維持のために画面全体へ横スクロールを生じさせる方式Bは採用しない。
- **表示内容**：内部の長い文字列は必要に応じて折り返し・省略表示等を検討するが、**どちらを採用するか・どの要素に適用するかは未決**。入力内容が失われたり操作不能になったりしないことを受入観点として引き継ぐ。
- **例外境界**：テーブルなど意図的に内部スクロールを持つComponentの仕様を今回変更したものではない。
- **状態**：2.4.2進行中、基本動作一部承認、実装未着手・検証未実施。
- **次の議題**：長い表示文字列の扱い（折り返しと省略表示をどのように使い分けるか）。

### 2026-10-19：Component幅縮小時も文字サイズは維持（方式1・承認済み）

- **承認根拠**：「Componentの幅が縮小しても文字サイズは維持する方針」への選択肢「1. 維持する（推奨）」にユーザーが「1」と回答。
- **承認内容**：LayoutItemによるComponentの幅縮小に連動して、Component内部のフォントサイズを自動的に小さくしない。幅と文字サイズは別の制御とする。
- **適用の境界**：利用者のOS・ブラウザの文字サイズ設定やアクセシビリティ拡大を禁止するものではない。長い文字列の折り返し・省略表示・マーキーなどの採否はComponent種別ごとに未決。
