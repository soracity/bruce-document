## 実装後に作成するテスト成果物

### テストケース一覧

実装後に、少なくとも以下の項目を1ケース単位で管理する。

| 項目 | 内容 |
|---|---|
| テストケースID | 既存 `T-ARC-01` 等のT-IDを引き継ぐ。追加時は一意なIDと追加理由を記録 |
| 対応設計書 | ファイル名・章・仕様ID（例：`02章 / STYLE-01`）、必要に応じ該当節 |
| 実装対象 | `IMP-01` 等のIMP-IDと本番コードのファイル/クラス/メソッド |
| テスト内容 | 前提条件、入力・操作、期待結果、異常系と境界値（適用があれば） |
| テストコード | 本番コードに対するテストファイルとテスト名の相互参照 |
| 実行結果 | 実行環境・コミット・実行日時・Pass/Fail/未実施・根拠 |
| 変更履歴 | バグ/改修ID、変更理由、影響する仕様ID、追加・変更したテスト |

- **設計書の仕様項目 → テストケースID → テストコード → 実行結果**を追跡できるようにする。
- 逆方向の**テストケースID → 設計仕様・本番実装箇所**も追跡できるようにする。
- 1仕様に複数ケース、1ケースに複数の関連仕様を認めるが、対応関係を省略しない。
- 既存`14_テスト仕様.md`のT-IDと期待値を流用し、同じ条件のテストを重複生成しない。
- 新規テストケース一覧やテストコードの**実物は本番実装後に作る**。この文書は方針・管理項目のみを定義する。

### バグ・改修の運用

1. 不具合・改修要求にIDを割り振り、該当IMP-IDと設計書仕様IDを紐付ける。
2. 既存テストケースに該当するものがあれば結果を記録し、不足する再発防止ケースはテストケース一覧へ追加する。
3. 対応するテストコードを新規作成・変更し、本番コードを修正する。
4. 関連テストと必要な回帰テストを実行し、ケースIDと結果・コミットを記録する。
5. 要件自体を変更する改修など、FIX設計書に変更が必要な場合は、具体的差分の承認を経て設計書・対応関係を更新する。
