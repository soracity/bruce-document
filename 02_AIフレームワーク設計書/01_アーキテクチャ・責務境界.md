## 1. 画面から保存処理までの構造

```text
画面Component（表示制御・操作受付・画面状態）
  ├─ ItemStackLayout / LayoutItem / LayoutSpan（外側配置）
  │    └─ 共通Component（内部表示・FormControl接続・汎用イベント）
  ├─ UI Form DTO（FormGroup・画面入力状態）
  └─ Application（ユースケースの調整）
       ├─ Domain（業務判断・整合性・状態遷移）
       └─ Infrastructure（Repository実装・DB/REST/端末アクセス）
```

**依存方向の設計規則**：画面はApplicationを呼び出すが、DBへ直接アクセスしない。共通Componentは画面固有Applicationを呼ばない。DomainはAngular、SQLite、RESTに依存しない。InfrastructureはDomainの業務判断を肩代わりしない。

## 2. 各層の実装責務と禁止事項

| 実装場所 | 記述するもの | 記述しないもの | 判断例 |
|---|---|---|---|
| 画面Component TS | 画面状態、操作イベント、FormGroupとの接続、Application呼出し、処理結果の画面反映 | SQL、テニスのサーブ順などの業務判断、共通部品内部CSS | 保存ボタンを押したら入力を確認しユースケースを呼ぶ |
| UI Form DTO | 画面入力値、FormControl定義、画面入力Validation状態 | DBアクセス、画面遷移、業務判断 | 入力必須を管理 |
| 共通Component | 自身の内部UI、FormControl連携、汎用イベント通知 | 保存先や試合ルールの決定 | Textboxが入力値をFormControlへ伝える |
| LayoutManager | 外側の並び、gap、wrap、幅比率 | FormControl、disabledの業務判断、ラベル、保存処理 | TextboxとDateを70:30に並べる |
| Application | ユースケースの処理調整、DomainとInfrastructureの呼出し順序、結果の組立て | UI描画、CSS、SQLite固有SQL | 保存処理の呼出し順を調整 |
| Domain | テニスのルール、業務整合性、状態遷移 | Angular、SQLite、REST、画面表示 | サーブ順の正当性を判定 |
| Infrastructure | DB/REST/端末への技術アクセス | テニスのルール、画面表示判断 | SQLiteへの保存を実行 |

## 3. 画面レイアウトの実装方法

画面Componentは「何をどの順序で置くか」をテンプレートで記述し、「どう配置するか」のCSS実装はLayoutManagerへ任せる。以下は原典に記録された承認済みの記法例である。

```html
<app-item-stack-layout>
  <app-layout-item>
    <app-textbox [appLayoutSpan]="70" ... />
    <app-date [appLayoutSpan]="30" ... />
  </app-layout-item>
  <app-layout-item>
    <app-button ... />
  </app-layout-item>
</app-item-stack-layout>
```

- **ItemStackLayout**：行を縦方向に積み重ね、行間gapを管理。
- **LayoutItem**：1行の子要素の横並び、gap、wrapを管理。
- **LayoutSpan**：必要な場合だけ幅比率を指定。兄弟要素の幅比率の厳密な制約は[06 LayoutManager・静的検査](06_LayoutManager・静的検査.md)に従う。
- **TableContainerLayout**：表構造、列、横スクロール等のテーブル固有の外側管理。
- **共通Component**：内部padding、input、ラベル等の見た目・操作性を管理。
- **styles.scss / design token**：アプリ全体の色、文字、サイズ等のデザイン規則。

### 禁止する画面実装

```html
<!-- 禁止：画面側で任意CSSレイアウトを組み立てる -->
<div class="flex gap-4 mt-3 w-full">...</div>
<!-- 禁止：共通Componentの外部配置を直接CSSで上書き -->
<app-textbox class="w-1/2" ... />
<!-- 廃止方針：内部へ任意classを注入するAPI -->
<app-textbox classContainer="m-4" ... />
```

外側の配置はLayoutManager、内部の見た目は共通Componentで解決する。必要な見た目の差分は任意class文字列ではなく、承認された限定的な意味付きInputを使う。必要なAPIがなければ画面側で代替CSSを発明せず、設計課題として扱う。

## 4. 保存操作の責務別処理順（構造例・具体API未承認）

| 順番 | 実行主体 | 役割 | 例外・境界 |
|---:|---|---|---|
| 1 | 共通Button | クリックを汎用イベントとして画面へ通知 | ButtonがApplicationを直接呼ばない |
| 2 | 画面Component / UI Form DTO | 画面入力値・入力Validation状態を参照 | UI入力の検証と業務整合性を混同しない |
| 3 | 画面Component | Applicationのユースケースを呼ぶ | DBやDomain実装を直接呼ばない |
| 4 | Application | Domainによる業務ルール・整合性確認とInfrastructureの処理を調整 | 実際の呼出し順・失敗時の戻り値型は個別ユースケース設計が必要 |
| 5 | Infrastructure | Repository実装等でDB/RESTを実行 | SQLを画面へ漏らさない |
| 6 | 画面Component | Applicationの処理結果を画面状態へ反映 | 成功/失敗のUI表現・画面遷移条件は画面別仕様で定義する |

**未確定事項**：保存APIの具体的なメソッド名・引数・戻り値・エラー型、トランザクション境界、画面遷移条件はPhase 2.1だけでは決定されていない。これらを仮のコード例で「承認済みAPI」として固定しない。Form DTOの生成方式とValidation責務は[07 DTO・Form・ACG](07_DTO・Form・ACG.md)と[11 ACG型・Nullable・Validation詳細](11_ACG型・Nullable・Validation詳細.md)を参照する。

## 5. ComponentBaseとの接続

共通スタイルInputは`ComponentBase`で一元定義し、FormControlを必要とするComponentは`FormControlComponentBase<T> extends ComponentBase`を使用する。FormControl不要Componentは`ComponentBase`を直接継承する。子Componentの既定値はprotectedな取得メソッドをoverrideし、画面からの明示Inputを優先する。旧「単一ComponentBaseへ任意FormControlを統合する案」は撤回済み。

原典：[Phase 3.3](../01_ai-document/phase3_03_ComponentBase.md) 2026-10-20の正式承認。Signal Input継承の実装と既存FormControl変更検知の互換性はPhase 5で検証する。

## 6. 実装着手前の確認・検証観点

- 画面からDB/REST/SQLiteへ直接アクセスしていないこと。
- 共通Componentから画面固有Applicationを呼んでいないこと。
- DomainにAngularやSQLite等の依存がないこと。
- LayoutManagerがFormControlや画面固有業務判断を保持していないこと。
- 画面独自flex/grid/widthや共通Componentへの任意CSS注入による配置の迂回がないこと。
- FormControlComponentBaseの継承とInput既定値優先順位を実装・検証すること。
- 画面固有ユースケースのAPIとエラー処理は個別設計で確定し、未承認の仮実装を混入させないこと。
