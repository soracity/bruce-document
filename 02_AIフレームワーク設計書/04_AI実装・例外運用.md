# AI実装・安全停止・再開・CI・運用 詳細設計

## AI-01 実装指示の入力契約

AIへ渡す入力は、画面設計書、適用する詳細設計版、実装対象一覧、生成対象、使用可能API、対象ブランチ、受入試験。業務仕様が不足していれば独自Application APIを発明しない。通常の承認済み仕様範囲の実装・修正には都度承認不要。

```markdown
対象画面：
対象ブランチ/基準コミット：
適用するBruce詳細設計版：
画面設計書：
ACG入力定義/生成ファイル：
使用するLayout/共通UI：
入力DTO/表示DTO/Application契約：
画面イベントと表示条件：
実装対象外：
受入テストID：
```

画面は配置を記述し、LayoutManagerが配置のCSS実装を担う。appLayoutSpanは通常省略、比率要件がある場合だけ全兄弟へ明示し100。排他条件はelse if、反復はLayoutItem全体。部品内部のflex/gapと画面独自レイアウトを混同しない。

## AI-02 禁止事項

| 禁止 | 必要時の正しい変更先 |
|---|---|
| 画面の独自flex/grid/width/margin/breakpoint | LayoutManager仕様/実装 |
| classContainer/classInput/classLabel等の任意CSS注入 | 共通部品の限定Input/内部標準スタイル |
| TableCell.cellClassesの別名再導入 | AppUiColorEnumと共通固定変換 |
| 動的Tailwindクラス名組立て | 固定Map/switch/固定SCSS |
| 生成Enum/DTO/DAOの直接修正 | 定義・解析器・モデル・生成器・再生成 |
| Mapper/Converter/Assemblerの無断追加 | 画面Componentで明示変換 |
| FormControl値とeventKeyの型統合 | 値型と操作識別型の分離 |
| 業務ルールを共通UI/Layout/UI DTOに実装 | アプリ固有Application/Domain |
| タップ領域や最小寸法のAI補完 | 承認済み画面/部品寸法 |
| 未承認案を承認済みと表示 | 根拠・提案・未決の分離 |
| ビルド成功を実機試験合格と表示 | 実施した検証だけを記録 |

旧ToggleButtonとbrf9014-shared-componentsは現行16部品に戻さない。component-test/apidocは通常UI一覧と分け、設計例とAPI利用例を新仕様へ更新する。

## AI-03 標準作業フロー

1. 最新の議事録/進捗/詳細設計/中断記録とGit作業ツリーを確認。基準コミット・変更前ビルド状態を保存する。
2. 画面設計書の16列、必要Enum/ラベル、既存Application契約を確認する。
3. ACGが必要なら定義/生成器を修正→再生成→再生成直後の差分を独立して確認する。ACG互換移行では手修正前に再生成直後の状態を独立コミットとして履歴化し、そのSHAとエラー分類を記録する。生成物をその後手修正しない。
4. 共通型→基底→共通UI→Layout→Table/Swipe→画面の依存順に実装する。同一原因を画面ごとにcastで隠さない。
5. `npm run build`で公式検査→Angularビルド。該当テストIDを実行する。
6. 差分を人間がレビューできる形でまとめる。責務・CSS・生成元・型変換・保守性を確認する。
7. 実際に変更したファイル、実行コマンドと結果、未実施試験、残件を記録する。

## AI-04 逸脱時の安全停止

設計逸脱が必要と判明した時点で、その逸脱の実装を止める。まず承認済み案で解決できる手段を調査する。新しい基底/Mapper/型キャスト/CSS注入への切替をエラー回避として採用しない。

AI自身の未完了変更を正常化、または自分が変更した範囲だけ安全に戻す。他者の変更をgit reset等で巻き戻さない。変更前と同等のコンパイル/ビルド可能状態を原則確保する。既存エラーと今回増やしたエラーを分ける。

復旧・ビルド確認が不可能なら正常停止と報告せず、残る差分・エラー・安全な再開地点を記録する。安全に元へ戻した場合も、最初の案・失敗の経緯を消さない。

## AI-05 GitHubへ残す再開記録

議事録の対応工程へ日時付きで記録し、進捗表を同期する。議事録名はphase*.md。旧原文は削除・改変しない。

```markdown
### YYYY-MM-DD：実装中断/再開記録
- 工程ID・詳細設計版・承認済み原案：
- 基準コミットと変更ファイル：
- 完了作業/未完了作業：
- エラー再現条件・エラー全文・原因：
- 試した方法と各結果：
- ビルド/試験のコマンドと結果：
- 復旧した範囲・現在コミット・残る他者差分：
- 次回の具体的実装/検証手順：
- 採用禁止の迂回方法：
- 原案で進められない理由・影響・比較案：
- ユーザー判断が必要な項目：
```

次回はこの記録を最初に読む。設計変更が必要なら理由・影響・代替案を具体化して明示承認を得る。GitHub保存失敗を保存済みと報告しない。進捗表は現在位置・残作業の唯一の正本、議事録は議論履歴、詳細設計は実装契約として役割を分ける。

## CI-01 Push時CIの具体案

配置はアプリ側。実装サービス/実行環境の選択は今回の実装案であり、稼働済みではない。全開発Pushに必須成功を要求する保護ルールは自動追加しない。

```yaml
name: bruce-build
on: [push, workflow_dispatch]
permissions:
  contents: read
jobs:
  layout-and-angular:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22.12.0'
          cache: npm
      - run: npm install --global npm@11.6.2
      - run: npm ci
      - run: npm run build -- --project feature-20251212 --configuration production
      - run: node tools/create-build-evidence.mjs bundle --project feature-20251212 --configuration production --out evidence/dist.tar
      - id: bundle
        uses: actions/upload-artifact@v4
        with:
          name: bruce-bundle-${{ github.sha }}-${{ github.run_id }}-${{ github.run_attempt }}
          path: evidence/dist.tar
          if-no-files-found: error
      - run: node tools/create-build-evidence.mjs manifest --project feature-20251212 --configuration production --bundle evidence/dist.tar --out evidence/evidence.json
        env:
          BRUCE_ARTIFACT_ID: ${{ steps.bundle.outputs.artifact-id }}
          BRUCE_ARCHIVE_SHA256: ${{ steps.bundle.outputs.artifact-digest }}
      - uses: actions/upload-artifact@v4
        with:
          name: bruce-evidence-${{ github.sha }}-${{ github.run_id }}-${{ github.run_attempt }}
          path: evidence/evidence.json
          if-no-files-found: error
```

Node/npmはアプリpackage/lockfileの互換範囲を実装時に検査する。依存の最新版追従をこの作業で実施しない。CI診断はGitHub Actionsログへ残す。テストジョブ追加・PRトリガー・通知先へのメッセージ送信は未承認の運用を自動追加しない。

## CI-02 正式公開のゲート

正式公開の前提は対象commit SHAが一致するCIの静的検査とAngularビルドの両方のsuccess。失敗・未実施・別SHA・旧成果物は公開不可。手元の直接npx ng build成功で置き換えない。

リリース処理はSHA・CI run ID/attempt・bundle artifact ID/ZIP digest・tar digest・lockfile hash・設計/ACG版をrelease manifestに固定する。公開処理があるリポジトリでmanifestを検査し、CIが一致しなければ終了する。実際のStore署名・配布先・アカウント・公開承認者はアプリの配布設計で確定する。文書更新だけでCI保護や配布完了を宣言しない。

## OPS-01 受入・保守性・運用への引継ぎ

Phase 7はユーザーが選んだ実画面を使う。既存サンプルを実装できたことだけで実画面の受入としない。人間がレイアウト比率変更・項目追加・色変更・Validation変更を、独自CSSや生成物手修正なしに行えるか確認する。変更先・理由・差分・テストを説明できることを評価する。

Phase 8は設計版、共通部品commit、ACG commit、適用画面、導入手順、既知制限、検証証跡を対応付ける。仕様変更は根拠/承認→議事録→詳細設計→生成定義/実装→テスト→進捗の順に同期する。運用開始の範囲/時期はユーザーが判断し、文書作成時点で開始済みにしない。

テスト：T-AI-01〜05、T-CI-01〜04、T-MAINT-01〜03。担当者・配布先未決は運用開始の残件であり、テニスDomain設計をフレームワークへ戻す理由にしない。
